# 目標設計: LIFT JOB 広告通知・Base反映の完全化（2026-09-16）

## 対象クライアント

- 株式会社PM Agent
- 対象サービス: LIFT JOB

## 目標

Meta広告とChatGPT広告からのLIFT JOB応募について、Lark通知へ媒体・キャンペーン等を表示し、LIFT JOB Baseへ同じ経路情報を欠落なく保存する。ChatGPT広告は `oppref` だけの着地でも広告流入として識別し、OpenAI Conversions APIへ応募完了を返す。

## 完了条件

1. Meta広告の応募を想定した入力で、Lark通知が配置名を含む広告表記になり、Baseで `media_name=Meta広告` とUTM・広告ID群を確認できる。
2. ChatGPT広告の応募を想定した入力で、Lark通知が `ChatGPT広告（cpc）` になり、Baseで `media_name=ChatGPT広告`、`application_source=openai(ad)`、UTMを確認できる。クリック識別子 `oppref` はBaseへ複製せず、OpenAIへの成果返却だけに使う。
3. `oppref` だけの着地でも `utm_source=openai` / `utm_medium=cpc` として扱い、自然流入へ誤分類しない。
4. LIFT JOB応募APIが `oppref` をOpenAI Conversions APIへ渡す。`oppref` がない応募は送信しない。
5. LIFT JOB Baseに必要な受け皿が存在し、型・選択肢・フィールド名をAPIで読み戻して確認できる。
6. ローカルで `npm test`、`npm run typecheck`、`npm run build` が成功する。
7. main反映後、`ridejob-entry` と `ridejob-form` の最新productionが対象Git SHAでREADYになり、認証付きhealthが `ready` を返す。
8. 個人情報を含まないMeta/ChatGPTテストを各1件だけ本番経路へ送り、Lark Webhook受理、Base実レコードの値、OpenAIのvalidate-only応答を実測する。テストBaseレコードは作成時のrecord IDを保持してID指定で削除し、同じsubmission IDが0件であることを確認する。
9. 応募単位の安定した `submission_id` でBaseをupsertし、ブラウザ再送時の重複レコードを防ぐ。Meta/OpenAIのevent IDにも同じ値を使う。

## スコープ外

- 実在応募者データの変更
- 広告予算、配信ON/OFF、クリエイティブの変更
- Larkの新規Baseや外部サービスの新規リソース作成
- OpenAI AdsのAdvanced Matching有効化（第三者への個人データ提供を伴うため、既定OFFを維持）

## 戻し方

- コードは本変更コミットをrevertし、直前のREADYなproductionへrollbackする。
- Baseへ追加した選択肢・列は変更前スキーマを記録し、本変更で作った未使用項目だけを対象に戻す。既存応募レコードは変更しない。
- 本番テストは一意な `LIFT-E2E-20260916-*` を使い、読み戻し後にテストレコードだけを削除する。
